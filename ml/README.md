# ML-сервис скоринга

Сервис оценки кредитоспособности малого и микробизнеса для «Умного кредитного кабинета предпринимателя».

## Назначение

ML-сервис принимает заявку целиком (сущность `ApplicationIn`) и возвращает скоринг в формате, совместимом с фронтендом кабинета. Сервис работает в двух режимах: полный скоринг (после получения истории бюро) и предварительный (до отправки заявки, только по реестру).

## Зачем отдельный контейнер

ML вынесен в отдельный контейнер `ml` по следующим причинам:
- Изоляция зависимостей (scikit-learn, pandas, numpy) от основного backend
- Независимое масштабирование и развертывание модели
- Модель и конфигурация упаковываются в образ вместе с кодом для воспроизводимого запуска без переобучения
- Отдельный healthcheck и управление жизненным циклом

## Два режима работы

| Режим | Эндпоинт | Описание |
| --- | --- | --- |
| **Полный (`full`)** | `POST /score` | Требует данные истории бюро и реестра. При отсутствии истории или реестра возвращает `422 MISSING_DATA`. |
| **Предварительный (`preliminary`)** | `POST /score/preliminary` | Работает только с данными реестра. История бюро игнорируется (факторы по истории не показываются). Подходит для быстрой оценки на шаге «Вариант». |

## Расчёт скоринга

### 1. Вход
Сервис принимает полную сущность заявки `ApplicationIn`. Из блока `applicationScore` (или напрямую) извлекаются:
- `history` (данные бюро: кредитная история, банкротство, случаи просрочки)
- `registerInfo` (данные реестра ЕГРЮЛ/ЕГРИП)

Схема поддерживает как новый формат с `applicationScore`, так и старый, с игнорированием неизвестных полей.

### 2. Признаки
Признаки рассчитываются в `app/features.py` из данных заявки:

| Признак | Описание |
| --- | --- |
| `business_age_months` | Возраст бизнеса в месяцах (от даты регистрации до даты заявки) |
| `is_sole_proprietor` | Форма собственности (ИП/ООО) по ОГРН/КПП |
| `okved_group` | Группа ОКВЭД (торговля/производство/услуги/прочее) |
| `avg_revenue_monthly` | Среднемесячная выручка (`annualIncome / 12`) |
| `expense_ratio` | Доля расходов (`annualExpenses / annualIncome`) |
| `revenue_cv` | Коэффициент вариации остатков по счёту (стабильность оборота) |
| `employees_count` | Численность сотрудников |
| `bank_client_months` | Стаж клиента банка |
| `active_loans_count` | Количество действующих кредитов (статус не PAID) |
| `debt_service_ratio` | Долговая нагрузка (платежи по активным кредитам / выручка) |
| `delayed_payment_cases` | Количество случаев просрочки |
| `requested_to_monthly_revenue` | Отношение запрошенной суммы к месячной выручке |
| `term_months` | Срок кредита в месяцах |

Обязательные поля зависят от режима. При отсутствии обязательных данных возвращается `422` с кодом `MISSING_DATA` и списком недостающих полей.

### 3. Модель
Используется **логистическая регрессия** (scikit-learn) в пайплайне с предобработкой:
- Числовые признаки: импутация медианой, стандартизация
- Категориальные (`is_sole_proprietor`, `okved_group`): импутация модой, one-hot кодирование

Модель обучается на синтетических данных генератором `train/generate.py`. Артефакты модели хранятся в `model/`:
- `logreg-0.1.joblib` - обученный пайплайн
- `meta.json` - метаданные (признаки, медианы, моды, диапазоны для клиппинга, версия)
- `metrics.json` - метрики на тестовой выборке

### 4. Расчёт балла
PD модели преобразуется в балл по формуле из дизайна кабинета:
```
pd = 0.45 / (1 + exp((score - 48) / 8))
score = 48 + 8 * ln(0.45 / pd - 1)
```
- При `pd >= 0.45` балл = 0
- При `pd <= 0` балл = 100
- Результат ограничивается диапазоном 0-100 и округляется

Класс риска определяется по баллу: A (>=80), B (>=70), C (>=60), D (>=45), E (<45).
Надбавка к ставке: >=80 -> -1 п.п., 60-79 -> +1 п.п., 45-59 -> +3.5 п.п., <45 -> +6 п.п.

### 5. Факторы
Факторы объяснения рассчитываются методом «что было бы при типичном значении»:
- Для каждого признака сравнивается балл при реальном значении vs балл при замене на типичное (медиана для числовых, мода для категориальных)
- Балл фактора = разница баллов (плюс повышает шанс одобрения)
- Показываются до 7 факторов с ненулевым вкладом, отсортированных по модулю влияния
- Стоп-факторы имеют приоритет и не дублируются модельными факторами
- Для отрицательных факторов обязательно предоставляется совет (`advice`)
- При клиппинге выбросов добавляется примечание

Стоп-факторы (ограничивают балл до `stop_factors.score_cap = 30`, класс E):
- Компания не действует (`isActive = false`)
- Банкротство (`bankrupt = true`)
- Молодой бизнес (< 6 месяцев)
- Много просрочек (> 3 случаев)

## Запуск

### Локально (разработка)
```bash
cd ml
python -m venv .venv
.\.venv\Scripts\activate  # Windows
pip install -r requirements-dev.txt
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

### Через Docker Compose
```bash
docker compose up --build ml
```

Сервис будет доступен на `http://localhost:8000`. Healthcheck: `GET /health`

### Пример запроса
```bash
curl -X POST http://localhost:8000/score \
  -H "Content-Type: application/json" \
  -d @tests/fixtures/application_full.json
```

### Пример ответа
```json

  "pd": 0.12,
```

## Переобучение

Для переобучения модели на синтетических данных:

```bash
cd ml
# Генерация данных
python -m train.generate

# Обучение модели
python -m train.train_logreg
```

Модель, метрики и метаданные сохраняются в `model/`. Команда воспроизведения должна давать детерминированный результат при фиксированном seed.

## Конфигурация

Конфиги находятся в `config/`:

| Файл | Назначение |
| --- | --- |
| `scoring.yaml` | Пороги баллов, классы риска, надбавки к ставке, стоп-факторы, пороги для интерфейса |
| `labels.yaml` | Тексты факторов (заголовки, описания, советы) с шаблонами подстановки |
| `okved_groups.yaml` | Группировка кодов ОКВЭД по сферам деятельности |

Конфиг валидируется при старте. При ошибке конфигурации сервис падает с понятным сообщением.

Эндпоинт `GET /thresholds` отдаёт пороги для использования backend'ом.

## Данные и ограничения

### Данные
- **Только синтетические данные.** Обучающий датасет генерируется скриптом `train/generate.py`. Никаких реальных данных клиентов не используется.
- **Данные в репозитории не коммитятся.** Сгенерированные CSV-файлы в `train/data/` игнорируются git.
- **Метрики демонстрационные.** ROC AUC, PR AUC и другие метрики рассчитаны на синтетических данных и не отражают реальную производительность модели.

### Формула метки и подбор распределения
Метка дефолта в генераторе рассчитывается по логистической формуле с весами, отражающими влияние признаков (возраст бизнеса снижает риск, просрочки и долговая нагрузка повышают риск, залог слегка снижает риск). К шуму добавляется случайность для реалистичности.

Подбором свободного члена и масштаба шума добиваемся:
- Средняя доля дефолтов ~8-10%
- Распределение баллов: ~15-25% заявок с баллом >=75 (автоодобрение), ~55-65% в диапазоне 45-74, ~15-20% <45 (отказ)

Эти цифры подобраны для демонстрации всех сценариев в хакатоне, а не являются статистикой по реальному портфелю.

### Допущения
См. раздел 3 плана `ML_AGENT_PLAN.md`:
- В данных нет числа дней просрочки, используется количество случаев просрочки
- `lastYearBalances` - остатки по счёту, коэффициент вариации служит заменителем нестабильности выручки
- Границы надбавки к ставке по баллу предположительные
- Данные по арбитражу, налоговой задолженности и санкциям в модель не входят (пока не передаются backend'ом)
- При отсутствии необязательных данных признак заменяется типичным значением, фактор не показывается
- В полном режиме требуются и история, и реестр; в предварительном режиме история не требуется
