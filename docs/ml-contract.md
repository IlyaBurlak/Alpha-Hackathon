# Контракт ML-сервиса `/score`

Документ описывает, зачем нужен ML-сервис, как с ним общается backend и какие решения закреплены в контракте.

**Статус:** сервис отвечает заглушкой (`model_version: "stub-0.0"`). Контракт зафиксирован и при замене заглушки на обученную модель меняться не будет.

## Назначение и место в архитектуре

ML-сервис оценивает вероятность дефолта (PD) по заявке малого бизнеса и возвращает пять главных факторов, повлиявших на оценку. Он ничего не решает: зону риска, условия и отказ определяет движок правил в backend. Скоринг даёт оценку риска, а решение учитывает ещё продукт, сумму, срок и внутренние ограничения банка.

Сервис вынесен в отдельный контейнер (`ml`, FastAPI), потому что у модели свои зависимости и свой ритм изменений. Благодаря фиксированному контракту backend и ML работают параллельно: backend подключается к заглушке и не ждёт обученную модель.

```
backend (оркестратор) --POST /score--> ml (FastAPI) --> pd + топ-5 факторов
                      <---------------
backend (движок правил): pd + стоп-факторы + лимиты продукта --> зона риска и решение
```

## Эндпоинты

| Метод и путь | Назначение |
|---|---|
| `POST /score` | Оценка заявки: PD и топ-5 факторов |
| `GET /health` | Проверка готовности, отвечает `{"status": "ok"}`; используется в healthcheck compose |
| `GET /docs`, `GET /openapi.json` | Swagger UI и OpenAPI-схема, генерируются из моделей сервиса |

Адрес внутри docker compose: `http://ml:8000` (переменная `ML_SERVICE_URL` у сервиса `server`). Снаружи для отладки порт проброшен как `localhost:8000`.

## Запрос `POST /score`

```json
{
  "application_id": "a-1024",
  "features": { "...": "11 признаков из таблицы ниже" }
}
```

Все 11 признаков обязательны. Если признака нет, backend не вызывает `/score`, а переводит заявку в статус «Нужны данные».

| Признак | Тип | Ограничение | Смысл | Откуда берёт backend | Влияние на риск |
|---|---|---|---|---|---|
| `business_age_months` | int | ≥ 0 | Возраст бизнеса, месяцы | ЕГРЮЛ (мок) | больше возраст, ниже риск |
| `is_sole_proprietor` | bool | | `true` для ИП, `false` для ООО | ЕГРЮЛ (мок) | ИП рискованнее |
| `okved_group` | enum | `trade`, `manufacturing`, `services`, `other` | Группа ОКВЭД | ЕГРЮЛ (мок) | торговля рискованнее производства |
| `avg_revenue_12m` | float | ≥ 0 | Средняя месячная выручка за 12 мес, руб. | выписка CSV | выше выручка, ниже риск |
| `revenue_cv` | float | ≥ 0 | Коэффициент вариации выручки (разброс по месяцам) | выписка CSV | выше разброс, выше риск |
| `expense_ratio` | float | ≥ 0 | Доля расходов в выручке, доля от 1 (0.7 = 70%) | выписка и анкета | выше доля, выше риск |
| `debt_service_ratio` | float | ≥ 0 | Платежи по действующим кредитам к выручке, доля от 1 | анкета и БКИ (мок) | выше нагрузка, выше риск |
| `max_delinquency_days_12m` | int | ≥ 0 | Максимальная просрочка за 12 мес, дни | БКИ (мок) | больше просрочка, выше риск |
| `active_loans_count` | int | ≥ 0 | Число активных кредитов | БКИ (мок) | больше кредитов, чуть выше риск |
| `requested_to_monthly_revenue` | float | ≥ 0 | Запрошенная сумма, делённая на среднемесячную выручку | анкета | больше отношение, выше риск |
| `term_months` | int | ≥ 1 | Срок кредита, месяцы | анкета | зависимость нелинейная |

Колонка «Влияние на риск» описывает ожидаемое направление для реальной модели. Заглушка его не использует.

## Ответ

```json
{
  "pd": 0.071,
  "model_version": "stub-0.0",
  "factors": [
    { "feature": "revenue_cv", "label": "Нестабильная выручка", "impact": 0.021 }
  ]
}
```

- `pd`: вероятность дефолта за 12 месяцев, число от 0 до 1.
- `model_version`: версия модели; backend сохраняет её вместе с результатом скоринга, чтобы решение можно было воспроизвести.
- `factors`: топ-5 факторов. `label` написан по-русски и готов к показу сотруднику банка. `impact > 0` повышает риск, `impact < 0` снижает.

Количество факторов (ровно пять) закреплено соглашением, схема ответа его не проверяет.

## Ошибки

Невалидный запрос (нет признака, значение вне ограничения, неизвестная группа ОКВЭД) даёт `422` со стандартным телом FastAPI: список ошибок с указанием поля. Backend трактует любой ответ, кроме `200`, и таймаут как «ML недоступен». Что делать дальше, решает сценарий backend. По итогам созвона 21 октября оператор видит предупреждение и выбирает: повторить, подождать или разобрать вручную.

## Поведение заглушки

Заглушка нужна, чтобы backend и frontend проходили весь путь заявки без обученной модели, поэтому она умеет возвращать значения для разных зон:

| Условие | `pd` |
|---|---|
| `max_delinquency_days_12m > 30` | 0.45 |
| иначе, если `requested_to_monthly_revenue > 4` или `revenue_cv > 0.6` | 0.18 |
| иначе | 0.071 |

Список факторов в заглушке фиксирован и от входных данных не зависит. Пороги `pd` заглушки не являются порогами зон риска: их задаёт конфиг backend.

## Принятые решения

1. **11 признаков вместо 7.** Пример в исходном документе содержал 7 признаков, таблица ML-составляющей 11. Чтобы не менять контракт позже, заложены все 11.
2. **Доли хранятся как числа от 0 до 1**, а не как проценты. Выручка в рублях.
3. **ML отдаёт оценку, а не решение.** Так банковская логика (продукт, лимиты, стоп-факторы) остаётся в прозрачных правилах, а модель можно менять независимо.
4. **Контракт не зависит от модели.** Заглушку, логистическую регрессию и LightGBM можно подменять без изменений в backend: меняются только `model_version` и содержимое `factors`.
5. **Все данные синтетические.** Реальных клиентских данных нет, поэтому метрики будущей модели будут демонстрационными и так подписаны в README.

## Открытые вопросы

- **Текстовый комментарий к оценке.** На созвоне 21 октября обсуждалось, что ML отдаёт комментарий вместе с ответом. В текущем контракте такого поля нет. Если оно нужно, его можно добавить как необязательное поле `comment` без поломки существующих клиентов. Решение за командой.
- **Единицы `avg_revenue_12m`.** Принято: средняя месячная выручка за 12 месяцев. Backend должен считать признак по выписке так же.

## Как проверить

Swagger: открыть `http://localhost:8000/docs`, выбрать `POST /score`, нажать Try it out и отправить пример запроса. Ожидаемый ответ: `pd`, `model_version` и пять факторов.

Из консоли (bash или `curl.exe` в PowerShell):

```bash
curl -X POST http://localhost:8000/score -H "Content-Type: application/json" -d @request.json
```

Здесь `request.json` содержит пример запроса из раздела «Запрос» с заполненными 11 признаками. Проверка граничных случаев: при `max_delinquency_days_12m: 45` приходит `pd: 0.45`, при `term_months: 0` приходит `422`.
