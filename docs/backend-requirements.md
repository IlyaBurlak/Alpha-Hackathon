# Что нужно доделать бэкенду (`server/`) под дизайн кабинета

Полный пошаговый список данных по экранам, включая ML, — в [`backend-data-contract.md`](./backend-data-contract.md); ниже — приоритеты и ошибки текущего API.

Клиент собран по дизайну «Кредитный кабинет МСБ». Чего не хватает на бэке, перечислено ниже. Пока бэк этого не отдаёт, на клиенте стоят моки (см. [`frontend-mocks.md`](./frontend-mocks.md)); как только поле приходит с бэка, оно имеет приоритет над моком.

Условные обозначения: **P1** — ломает или обедняет основной сценарий, **P2** — нужно для полного соответствия дизайну, **P3** — желательно.

## 1. Ошибки текущего API (P1)

| # | Что происходит | Что нужно |
| --- | --- | --- |
| 1.1 | `ApplicationEntity` не копирует `productId` и `productConditions` из модели, поэтому `GET /applications/:id`, `GET /applications/my` и `PUT /applications` никогда не возвращают выбранный продукт. Из-за этого же проверка «Продукт уже выбран» в `confirmApplication` не срабатывает, и продукт можно выбрать повторно. | Отдавать `productId` и `productConditions` (`{ name, persentage, payments }`). Клиент читает именно эти поля. |
| 1.2 | `GET /applications/:id` и `PUT /applications` для уже отправленной заявки прикладывают список `products` (из-за п. 1.1). | Не считать предложения для заявок не в статусе `DRAFT`. |
| 1.3 | Все ошибки приходят как `500 { error }`: «Нет доступа к заявке», «Заявка не найдена», «Продукт уже выбран». | Нормальные коды: 400 / 403 / 404 / 409. Клиент показывает `error` как есть. |
| 1.5 | Мок единого реестра слушает `/invidual` (опечатка), а `GatewayService` ходит на `/individual`: данные по ИП не приходят. | Исправить путь в одном из двух мест. |
| 1.4 | `loanIssuanceDate` по умолчанию равен дате создания, хотя кредит не выдан. | `null`, пока кредит не выдан. |

### 2.2. Оценка («шанс одобрения»)

Дизайн на шаге 1 показывает по каждому варианту шанс одобрения (4 деления), «рекомендуем», круговую шкалу 0–100 и факторы с баллами. Для этого нужно, чтобы владелец заявки (а не только оператор через `GET /applications/:id/score`) получал:

```jsonc
// в каждом предложении из products (шаг 1) и в самой заявке (после рассмотрения)
"scoring": {
  "score": 72,                       // 0..100, выше — лучше (из pd ML-сервиса)
  "factors": [
    { "title": "Возраст бизнеса", "description": "6 лет на рынке", "points": 15 },
    { "title": "Кредитная история", "description": "Есть просрочка до 30 дней", "points": -10,
      "advice": "Закройте просрочку, через 3 месяца оценка вырастет" }
  ]
}
```

Метки («Высокий» от 80, «Хороший» от 60, «Средний» от 45, иначе «Низкий») и «Рекомендуем» клиент считает сам. Сейчас `mlScore.pd` ставится заглушкой (`pd: 0.1`, `factors` — список строк), и в заявку не попадает: см. также `getMlScoring`, результат которого не используется.

## 3. Кабинет сотрудника (`/staff`)

Кабинет сделан по дизайну «Кабинет сотрудника. Бизнес-кредиты». **Оператор бэкенда уже работает с реальными ручками**: вход, `GET /users/admin-info`, `GET /applications/all`, `GET /applications/:id/score`, `POST /applications/:id/take`, `POST /applications/:id/solution`. Статусы, ответственный, особое предложение и ответ клиента (`PUT /applications/:id/special`) тоже реальные. Что клиент всё ещё берёт из моков, см. [`frontend-mocks.md`](./frontend-mocks.md). | 3.3.1 | `PATCH /staff/applications/:id/assignee` `{ "employeeId": "u1" \| null }` | Назначить или снять ответственного; запись в историю («Назначен ответственный», «Ответственный снят»); возвращает заявку. | P1 |
| 3.3.2 | `POST /staff/applications/:id/decision` `{ type, comment, ... }` | Принять решение: `approve`; `offer` (`amount`, `termInMonths`, `rate`); `clarify` (`documents[]`, комментарий не короче 10 символов); `reject` (`reason`, комментарий не короче 10 символов). | 3.3.3 | `DELETE /staff/applications/:id/decision` | Отменить `offer` или `clarify` и вернуть заявку в `ready` (кнопка «Изменить решение»); запись «Решение отменено для пересмотра». | P2 |

### 3.4. Связь с кабинетом клиента

Решение сотрудника должно доходить до клиента (сейчас эти кабинеты никак не связаны):

- `approve` → заявка клиента `APPROVED` (кнопка «Подписать договор» из п. 2.1.8), `reject` → `REJECTED` с причинами для блока «Отказ» (`scoring.factors` с советами, п. 2.1.9);
- `offer` → клиент видит новые условия и может принять или отказаться (новые статусы и эндпоинты на стороне клиента);
- `clarify` → клиент видит список документов и комментарий и может загрузить их; ответ клиента попадает в историю заявки у сотрудника («Ответ клиента появится в истории»);
- `reviewStage` клиента (п. 2.1.6) выводится из статуса скоринга.

### 3.5. Прочее

- Уведомление «скоринг завершён» сейчас строится на клиенте сравнением списков; лучше событие или поле `scoring.finishedAt`.
- Список «Мои заявки» и «Решённые» клиент собирает из общего списка; при большом объёме нужны фильтры и страницы: `GET /staff/applications?status=&assigneeId=&q=&sort=&page=`.
- Во всех эндпоинтах роли проверяет сервер; клиентские охранники экранов нужны только для навигации.
