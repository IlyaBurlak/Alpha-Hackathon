Бекенд часть приложения для Альфа хакатона

## Общая архитектура
В качестве архитектуры выбрана микросервисная архитектура. Функциональность приложения разбита на модули по категориям. Для каждой такой категории в папке api есть отдельная папка, содержащая контроллер, сервис и репозиторий (по необходимости). Ниже приведы более подробные описания модулей и их api.

## Описание API
### Users
Модуль отвечает за работу с пользователями.

#### Метод авторизации пользователя
> POST /api/users/login

Тело запроса должно содержать логин и пароль пользователя, который пытается авторизоваться. 
Пример тела запроса: 
<pre>
{
    "login": "user",
    "password": "1234"
}
</pre>
При успешной авторизации возвращается токен для дальнейшего взаимодействия с системой. Длительность действия токена - 1 сутки с момента получения.
Пример ответа: 
<pre>
{
    "token": "abc123"
}
</pre>


#### Метод авторизации оператора
> POST /api/users/admin-login

Тело запроса должно содержать логин и пароль пользователя, который пытается авторизоваться. 
Пример тела запроса: 
<pre>
{
    "login": "user",
    "password": "1234"
}
</pre>
При успешной авторизации возвращается токен для дальнейшего взаимодействия с системой. Длительность действия токена - 1 сутки с момента получения.
Пример ответа: 
<pre>
{
    "token": "abc123"
}
</pre>

#### Получение информации о текущем пользователе
> GET api/users/info


Метод предоставляет информацию для отображения о текущем пользователе, а также список организаций, к управлению финансами которых у него есть доступ - между ними он может свободно переключаться в ходе работы с приложением. 

Пример ответа:
<pre>
{
    "login": "alfaAngelika",
    "fullName": "Василенко Анжелика",
    "organizations": [
        {
            "inn": "5001234569",
            "fullName": "ООО \"Кот не знает\"",
            "type": "OO",
            "id": 2
        }
    ],
    "id": 2
}
</pre>


### Applications
#### Создание заявки 
> POST api/applications/

Выполняется от зарегестрированного пользователя и только для одной из "его" организаций. После создания нужно будет выбрать один из доступных продуктов, только после этого заявка отправится на проверки и согласования.
Пример тела запроса: 
<pre>
{
    "organizationId":2,
    "sum": 100000000,
    "creditTime": {
        "units": "YEAR",
        "value": 1
    }
}

</pre>

credit time - время, на которое предполагается взять кредит. Возможные варианты измерения: "YEAR", "MONTH", "DAY". value - количество этих единиц (в примере - 1 год)

sum - запрашиваемая сумма в рублях
Пример ответа:

products - массив доступных для этой заявки продуктов с подсчитанными на основе запрошенной суммы суммой залога, условиями выплат и т.п. (рассчет произведен на основе мок-алгоритма). Пользователю предлагается выбрать подходящий

Если массив products пустой ([]) - подходящих продуктов нет.
Если атрибут products отсутствует - сервисы банка недоступны, зайдите в заявку и выберите продукт позже.

#### Выбор продукта для заявки
> PUT api/applications/?applicationId=4&productId=1

productId - взять из products при создании заявки. Если выбрать недоступный для этой заявки продукт, будет возвращена ошибка. Если в момент сохранения продукта сервисы банка будут недоступны для проверки - будет возвращена ошибка с предложением попробовать позже. 

При выполнении этого дейтвия заявка автоматически переходит в статус SUBMITTED, после чего запускается скоринг. Скоринг состояит из трех частей: 1 - запрос данных из бюро кредитных историй. 2 - запрос данных из единого государственного реестра. 3 - скоринг с помощью мл модели. После каждого этапа сохраняется статус и поолученная информация в атроибуте applicationScore (его может просматривать только админ, подробнее он описан ниже)

}
</pre>

> GET api/applications/my

Пример ответа: 
<pre>

    {
        "id": 1,
        "userId": 2,
        "organizationId": 2,
        "sum": 100000000,
        "status": "DRAFT",
        "createdAt": "2026-10-22T20:32:53.515Z",
        "creditTime": {
            "units": "YEAR",
            "value": 1
        },
        "loanIssuanceDate": "2026-10-22T20:32:53.515Z"
    },
    ....
]
</pre>

Возможные статусы заявки: 

*   DRAFT - заявка создана, продукт не выбран,
*   SUBMITTED - выбран продукт, заявка отправлена на проверку и подтверждение в банк,
*   APPROVED - заявка на кредит одобрена,
*   REJECTED - заявка отклонена


к каждой заявке может быть добавлена информация о продукте, если он выбран (формат такой же, как в запросе на получение конкретной заявки)

#### Ручной перезапуск скоринга 
Только для авторизованного оператора
> PUT /api/applications/{id}/restart
id заявки
Ответом будет true если перезапуск прошел успешно. Метод асинхронный, вероятно true придет раньше чем скоринг выполнится.
Запустить скоринг можно только для заявки в статусе SUBMITED.
Скоринг будет перезапущен целиком: будут запрошены данные кредитной истории, реестра, запущена мл-модель. Новые данные запишутся поверх старых. Было принято не хранить историю скорингов, так как важны для оператора только самые актуальные данные по компании.
