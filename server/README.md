Бекенд часть приложения для Альфа хакатона

## Общая архитектура
В качестве архитектуры выбрана микросервисная архитектура. Функциональность приложения разбита на модули по категориям. Для каждой такой категории в папке api есть отдельная папка, содержащая контроллер, сервис и репозиторий (по необходимости). Ниже приведы более подробные описания модулей и их api.

## Описание API
Также представлена в виде swagger документации. Но в этом текстовом файле расписано подробнее.

### Users
Модуль отвечает за работу с пользователями.

#### Метод авторизации пользователя
> POST /api/users/login

Тело запроса должно содержать логин и пароль пользователя, который пытается авторизоваться. 
Пример тела запроса: 
<pre>
{
    "login": "user",
    "password": "1234"
}
</pre>
При успешной авторизации возвращается токен для дальнейшего взаимодействия с системой. Длительность действия токена - 1 сутки с момента получения.
Пример ответа: 
<pre>
{
    "token": "abc123"
}
</pre>


#### Метод авторизации оператора
> POST /api/users/admin-login

Тело запроса должно содержать логин и пароль оператора, который пытается авторизоваться. 
Пример тела запроса: 
<pre>
{
    "login": "user",
    "password": "1234"
}
</pre>
При успешной авторизации возвращается токен для дальнейшего взаимодействия с системой. Длительность действия токена - 1 сутки с момента получения.
Пример ответа: 
<pre>
{
    "token": "abc123"
}
</pre>

> GET api/users/info

Модуль работы с заявками.

> GET api/applications/my

Пример ответа:

    {

        "sum": 100000000,

            "value": 1

Возможные статусы заявки: 

*   DRAFT - заявка создана, продукт не выбран,
*   SUBMITTED - выбран продукт, заявка отправлена на проверку и подтверждение в банк,
*   APPROVED - заявка на кредит одобрена,
*   REJECTED - заявка отклонена
*   SPECIALPRODUCTOFFERED - отклонено, но предложена альтернатива
*   SPECIALPRODUCTACCEPTED - альтернатива принята пользователем
*   SPECIALPRODUCTREJECTED - альтернатива отклонена пользователем
*   SIGNED - все документы подписаны, ожидается начисление денег от банка

#### Создание заявки 
> POST api/applications/

Выполняется от зарегестрированного пользователя и только для одной из "его" организаций. После создания нужно будет выбрать один из доступных продуктов, только после этого заявка отправится на проверки и согласования.

Пример тела запроса: 
<pre>
{
    "organizationId":2,
    "sum": 100000000,
    "creditTime": {
        "units": "YEAR",
        "value": 1
    }
}

</pre>

#### Выбор продукта для заявки
> PUT api/applications/?applicationId=4&productId=1

productId - взять из products при создании заявки. Если выбрать недоступный для этой заявки продукт, будет возвращена ошибка. Если в момент сохранения продукта сервисы банка будут недоступны для проверки - будет возвращена ошибка с предложением попробовать позже.

#### Принятие специального предложения

В некоторых случаях при отклонении заявки оператор может предложить выдать кредит на каких-то особых условиях. В этом случае статус заявки перейдет в SPECIALPRODUCTOFFERED, а в атрибуте продукт появится информация о предложении банка. Пользователь может рассмотреть это предложение и принять или отклонить его.

>PUT api/applications/{id}/special?status=SPECIALPRODUCTACCEPTED

id - идентификатор заявки 

Метод доступен только для автора заявки. Возможные статусы: SPECIALPRODUCTACCEPTED, SPECIALPRODUCTREJECTED. Метод отработает только если текущий статус заявки SPECIALPRODUCTOFFERED.


#### Подписание договора 
>PUT api/applications/{id}/sign

Метод доступен только для автора заявки и только если заявка одобрена (или утверждено специально предложение банка). Изменяет статус заявки на "Кредит выдан".

#### Ручной перезапуск скоринга 
Рекомендован к использованию если при автоматическом скоринге внешние системы были недоступны и скоринг провести не удалось.Только для авторизованного оператора
> POST /api/applications/{id}/restart
id заявки
Ответом будет true если перезапуск прошел успешно. Метод асинхронный, вероятно true придет раньше чем скоринг выполнится.
Запустить скоринг можно только для заявки в статусе SUBMITED.
Скоринг будет перезапущен целиком: будут запрошены данные кредитной истории, реестра, запущена мл-модель. Новые данные запишутся поверх старых. Было принято не хранить историю скорингов, так как важны для оператора только самые актуальные данные по компании.

## Описание модели данных

### User и Operator
Содержат одинаковые поля: id, login, fullName, password. Пароль хранится в зашифрованном виде. Таблицы разделены на две, так как никогда не будет выполняться запрос, в котором нужны и те, и другие значения, соответсвенно и запрос информации о пользователе, и запрос информации об операторе будет выполняться быстрее.

### Organization
Информация об организаци, которая уже есть в банке. Поля: id, fullName, inn, ogrn, head (для простоты указано текстом фио, так как владелец может не быть клиентом банка), account (рассчетный счет), address, type (в коде используется enum - физ. или юр. лицо). Связана с пользователями многие-ко-многим через таблицу UserToOrganization

### Application
Информация о кредитной заявке пользователя. Поля: id, userId, organizationId, sum (сумма кредита), productId (идентификатор выбранного банковского продукта - сами продукты хранятся во внешней системе банка), productConditions (условия выбранного продукта в формате JSON, сохраняются в момент подачи заявки и останутся неизменными для пользователя до конца оплаты кредита), status (статус заявки, в коде используется enum), createdAt, creditTime (срок кредита: отдельные поля units и value), loanIssuanceDate (дата выдачи кредита), solutionComment (комментарий оператора), operatorId (идентификатор назначенного оператора).


### Application score
Информация по оценке заявки. Вынесена в отдельную таблицу, так как вероятно много пользователей будет заходить "просто посмотреть", будут создавать заявки, но не отправлять их на рассмотрение. Кроме того, в будущем предусмотрена система отзыва заявок. Таким образом при объединении этой таблицы с Application в одну была бы высокая вероятность большого количества пустых полей в базе данных. Поля: id, applicationId, scoringDate, creatingDate, score (итоговая оценка), status (статус обработки заявки, в коде - enum), info (JSON с данными кредитной истории, сведениями из реестра и подробно описанном результатом скоринга ML-моделью. Выбран такой формат так как эти данные никогда не используются отдельно друг от друга, а их формат в дальнейшем может измениться, например, если будет решено учитывать еще какой-то фактор при скоринге и он будет добавлен в данные из реестра или бюро). Результат ML-модели содержит pd (вероятность дефолта), score (балл), risk_class (класс риска), rate_premium_pp (надбавка к ставке в процентных пунктах), updated_at (дата обновления модели), model_version (версия модели) и factors (факторы, повлиявшие на оценку).
